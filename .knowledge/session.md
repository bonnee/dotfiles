# Graphical session startup (uwsm + Sway)

_Last verified: 2026-11-10._

Sway is started by **uwsm** from `~/.zprofile` when logging in on **tty1**.
Other VTs stay plain login shells.

## Flow at tty1 login

1. `~/.zprofile` exports `DBUS_SESSION_BUS_ADDRESS=unix:path=$XDG_RUNTIME_DIR/bus`
   if it is unset. Sway children must see it — the systemd user manager already
   has it, but a TTY login shell does not, and `libdbus` consumers (Spotify's
   tray code, libayatana-appindicator) hang without it.
2. `uwsm check may-start` → true only on VT1, local session, login shell,
   system at `graphical.target`, no active `graphical-session*.target`.
3. `exec uwsm start default` replaces the login shell with the session.
   Default compositor is `sway.desktop` (`~/.config/uwsm/default-id`).

Sway runs as `wayland-wm@sway.desktop.service` in `session.slice`; stop the
session with `uwsm stop` (not `swaymsg exit`).

## Consequences

- pywal/wpg colors: `~/.config/uwsm/env` sources `~/.cache/wal/colors.sh`, so
  the session (bemenu's `BEMENU_OPTS` theme, `FZF_DEFAULT_OPTS`, `LS_COLORS`)
  gets the generated palette at session start. Interactive shells source the
  same file from `.zshrc`. Because sway passes its own environment to children,
  a palette regenerated by wpg mid-session only reaches bemenu after a re-login.
- Tray apps: `syncthingtray` aborts with a "no tray area" error dialog if it
  starts before waybar registers `org.kde.StatusNotifierWatcher` — it is
  launched ~1 s after waybar. `app-syncthingtray@autostart.service.d/wait-for-tray.conf`
  adds an `ExecStartPre` that waits (max 10 s) for the watcher via `gdbus`, so
  the failure never happens; there is deliberately no restart loop, so a real
  failure shows at most one dialog.


- Stale session state: `graphical-session.target` / `sway-session.target` are
  **not** stopped when a sway that was started outside uwsm exits, which makes
  `uwsm check may-start` refuse to start ("A compositor and/or
  graphical-session* targets are already active"). `~/.zprofile` therefore has
  a fallback branch: on VT1, with no `sway` process running but
  `graphical-session.target` still active, it stops that target and starts the
  session. In a uwsm-managed session the stop is automatic
  (`wayland-session@…target` has `PropagatesStopTo=graphical-session.target`).
- `sway-session.target` is **not** wanted by `graphical-session.target`. It is
  started explicitly by Sway after `uwsm finalize`
  (`exec sh -c 'uwsm finalize && systemctl --user start sway-session.target'`),
  once `WAYLAND_DISPLAY` and `SWAYSOCK` are importable. The
  `~/.config/systemd/user/graphical-session.target.wants/sway-session.target`
  symlink was removed on 2026-11-10; do not re-add it. Under uwsm it starts
  swayidle/kanshi/polkit-gnome before `wayland-wm@sway.desktop.service`, and
  they fail to connect to the compositor (swayidle exits 253, then hits the
  start limit).
- `poweralertd.service` is wanted by `graphical-session.target` and starts
  before `mako`; it can fail with `could not send state update notification:
  No such device or address` and hit the start limit. A drop-in
  (`~/.config/systemd/user/poweralertd.service.d/restart-delay.conf`) sets
  `RestartSec=1s` and `StartLimitBurst=10` so it retries after `mako`. The unit
  remains ordered before `graphical-session.target`; moving it to
  `sway-session.target` with `After=mako` would be the ordering fix.
- `swayidle.service`'s `ExecStop` is guarded with
  `/bin/sh -c 'kill -9 "$$MAINPID" 2>/dev/null || true'` because `MAINPID` can
  already be unset at session shutdown.
- **polkit and the uwsm session.** Sway (and every GUI child, including
  waybar) lives in `user@123.service/session.slice/wayland-wm@sway.desktop.service`,
  which logind reports as the `manager-early` session
  (`loginctl list-sessions`: Class `manager-early`, no seat). Polkit cannot map
  such a process to a seat session, so policy defaults using
  `allow_active=yes` evaluate to no. This broke the Waybar power-profile
  switch: `tlp-pd` returns "Not authorized to switch profile" and the click
  does nothing. `pkcheck`/`tlpctl` from a TTY or SSH shell hit the same
  session and are denied too.
  Fix: `/etc/polkit-1/rules.d/50-tlp-pd.rules` allows user `bonnee` the
  `org.freedesktop.UPower.PowerProfiles.{switch,hold,release}-profile`
  actions. Polkit reloads `rules.d` by itself. Without the rule, use
  `sudo tlp {performance|balanced|power-saver}`.


- Environment: uwsm exports the env delta into the systemd + D-Bus activation
  environments. Session-only vars live in `~/.config/uwsm/env` (Wayland
  backends, MOZ_*, GTK_CSD). Machine-specific values (GDK_SCALE, QT_FONT_DPI,
  RUSTICL_ENABLE, ...) live in `~/.config/env/<hostname>/` — the same host
  directory `~/.zprofile` sources for login shells — and are applied by
  `~/.config/uwsm/env.d/90-host.sh`, which uwsm sources after `uwsm/env`, so
  the host value wins. uwsm sources `env-<desktop>*` after `env.d`, so a
  compositor-specific file would override the host layer. Because the host
  layer is shared with the shells, a TTY shell does see vars like GDK_SCALE;
  the Wayland toolkit backends stay session-only, so GUI apps must still be
  launched from inside the session.
- Session readiness: `exec uwsm finalize` in
  `~/.config/sway/config.d/80_autostart.conf` (sway does not `sd_notify`) plus
  `systemctl --user start sway-session.target`. `~/.config/env/wayland` used to
  run `xrdb ~/.Xresources`; that never fired (no `DISPLAY` at login) and is
  gone — use `exec xrdb -merge ~/.Xresources` in sway config if wanted.
- XDG autostart: `~/.config/autostart` and `/etc/xdg/autostart` entries run as
  generated `app-*@autostart.service` units in `app-graphical.slice`
  (`wayland-session-xdg-autostart@sway.desktop.target`, no longer masked).
  GNOME-only entries are filtered at start by `ExecCondition=` with
  `systemd-xdg-autostart-condition`. `dex` is no longer used; `nm-applet` comes
  from the autostart entry, not from sway's `exec` lines.
